# 设计决策

塑造了这个插件的若干选择，逐条短记。每条都写明当时考虑过的备选方案及其落选原因，
这样日后改动时能判断清楚：自己是在推翻一个决定，还是在重犯一个错误。

## D1 —— 由宿主判定，浏览器只负责呈现

**选用。** 宿主侧一个分类器读取 `turn/end`、`approval/request` 与
`user-questions/request`，把同一个事件分发给 Bark 和浏览器。

**否决。** 让浏览器从会话列表自行判定（`dsh-session-notification` 的做法）。它确实能用，但手机通道
无论如何都得自己判定——浏览器关着时没有别的可能——于是"这一轮到底算不算完成"的启发式会有两
份，并且必然漂移。何况浏览器也看不准排队中的工作和子 agent 树，精度不如宿主。

**后果。** 宿主插件加载失败，浏览器通道也跟着停。这一点接受：一个插件，一种失效模式。

## D2 —— 用受鉴权的 `/api` 路由，而不是自签令牌

**选用。** 在 `/api/dsh-notify/*` 下用 `ctx.connection.fetch.register`。Connection 只对属主 Peer
放行，并且请求本身已经携带浏览器会话；SSE 响应经 node:http 桥接流出。

**否决。** `ctx.webServer.register` 配一枚插件自签令牌（`dsh-push-notify` 的做法）。它的
`/dsh-push-notify/config` 路由不受鉴权保护：同一 tailnet 上的任何人都能读掩码配置、改写 device key，
或者触发测试推送。何况自签令牌本身也得经同一条不受保护的通道交给浏览器。

**后果。** 插件依赖 Connection 存在于组合中（`inject: ['connection']`）。

## D3 —— 插件自己持有一份 JSON 文档

**选用。** `$DSH_PROFILE_DIR/dsh-notify.json`，由宿主原子写入，经受鉴权的 API 以脱敏投影暴露给浏览器。

**否决。** 在 Loader 行上声明配置，并通过 `ctx.remote.settings` 写入。那是更原生的形态，还能白拿密钥
脱敏，但写入路径要么重启插件行（把实时流打断），要么依赖一条仅内存态的 Loader 路径——它的行为必须
先对着在跑的构建验证过才敢发版。而且一旦出现浏览器专属偏好，一份设置文档就会被拆成两个存储。

**后果。** 密钥成了插件的责任：它们不出宿主，掩码到后四位，只有显式 `null` 才能清除。不从任何前身插件
导入（见 D7）。

## D4 —— 自建设置页，而非生成的插件表单

**选用。** 一个 `settings.section` 页面，贴合 Harness 设置页的语言（几何、token、控件尺寸），并加上
生成表单做不到的东西：每条通道一个测试按钮、实时通道状态、逐类音效试听。

**否决。** 生成的配置表单再加一小块自定义状态。那是能做出的最小 UI，也是构造上最原生的，但它既不能
试听音效，也不能发一次测试推送——而这两件事恰恰是用户信任一个推送插件所需的——还会在同一页面留下两处
配置界面。

**后果。** 每个 DSH 次版本升级都要拿 Harness 设置外壳重新核对这个页面；几何之所以集中在一个样式模块里，
就是为了这件事。

## D5 —— 事件流不做重放

**选用。** SSE 是一条实时流，不处理 `Last-Event-ID`，也没有环形缓冲。

**否决。** 断线重连后重放错过的事件。通知描述的是某一个时刻；四分钟前的一次授权重放出来，等于诱使
人去处理一个已经过期的请求；而一条人早就读过的完成通知，重放只是噪音。

**后果。** 断开期间浏览器就是错过了那几张卡片；持久的那条是手机通道——手机本来干的就是这件事。

## D6 —— 一个包，三层内部结构

**选用。** `src/core`（纯逻辑，在 vitest 下运行）、`src/host`、`src/client`，作为一个 npm 包、一份
bundle patch 发布。

**否决。** 用 pnpm workspace 拆成各自独立版本号的多个包。插件很小，三层本来就一起发，单包能让安装始终
只有一行。

## D7 —— 不从前身插件导入

**选用。** 插件只持有自己那一份文档，别的什么都不读。文件不存在就用默认值。

**否决。** 首次运行时导入 `push-notify-config.json`（D3 最初描述的做法）。它让第一次启用显得无缝，
但也意味着每一次读取都要去理解第二份文档的结构，而且复制过来的分组名比"统一用 `DSH`"这个决定活得更久。
两个互不讲话的插件，比一条一次性翻译路径更好推理。

**后果。** 升级意味着打开一次设置页。前身的文件原封不动，两种走法都不会丢东西。

## D8 —— 通知读起来像这段对话

**选用。** 标题：一个状态标记加会话名。正文：这一轮里人最后输入的那句提问；定时或注入的回合没有提问，
于是回退到助手回答。失败与中断在 `·` 之后附上原因。

**否决。** 用助手最后一段收尾（更早的做法）。它读起来像在总结一份人并没要求出现在锁屏上的工作，而在手机上，
它还会去抢那个唯一能标识这条通知的东西：引发它的那句提问。

**后果。** 宿主必须监听 `user/message`，并留住最后一条 `source.kind` 为 `user` 的消息，这样注入的上下文
（定时任务、文件变更提示、目标续跑）永远不会变成正文。

## D9 —— 通道打开时才展开

**选用。** 总开关和两条安静规则排在最前；每条通道的设置只在它启用时才出现，逐类音效放在一张表里，
一列启用开关、一列浏览器音效、一列 Bark 铃声、一列试听。

**否决。** 永远可见的通道区块（更早的布局）。一半字段大多数时候是禁用的，那会让一个设置页看起来像是坏了，
而不是已经配好了。

## D10 —— 插件卡片在包里本地化，不在市场本地化

**选用。** `locale/en.json` 与 `locale/zh.json` 携带 `meta.title`、
`meta.description` 和 `meta.detail`。Harness 把英文文件当作词典的锚点，并读取它旁边的每种兄弟语言文件；
详情面板则按读者语言链的先后，取第一个声明了 Markdown `meta.detail` 的语言——于是中文读者看到的是
「会话通知」、一句中文，以及 `docs/DETAIL.zh.md` 而不是 README。

**否决。** 只本地化市场条目。市场（`dshmarket`）的卡片取自一条*目录条目*（awesome-dsh-plugin 仓库里的
`description.zh`），从不读包里的 locale 文件；而 Harness 插件页取自包，从不读目录。一个渠道服务不了另一个，
何况目录要等它的 npm 快照重新发布，才能触达中文安装。包是我们能控制的那一半，所以发出去的是这一半。

**后果。** 市场卡片会一直是英文，直到目录快照跟上；那是上游该修的事，不是这里的改动。`test/locale.test.ts`
钉住了这个问题静默失效的四种方式：缺 `en.json`、中文卡片照抄英文、`meta.detail` 指向包外或没随包发布，
以及 `files`/`exports` 列表把 locales 或文档漏掉。
